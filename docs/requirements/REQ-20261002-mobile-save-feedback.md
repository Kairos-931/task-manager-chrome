# 手机添加任务的保存状态反馈

- Status: in_development
- Date: 2026-10-02
- GitHub Issue: https://github.com/Kairos-931/task-manager-chrome/issues/66
- Source: 用户真实使用反馈“手机添加的时候没有显示保存成功失败等等状态”，要求记录。

## 问题与用户目标

用户点击手机页保存后无法判断是否正在处理、是否成功或失败，容易重复点击或重复添加任务。

## 推荐方向（待开发确认）

沿用当前手机添加页，不新增页面。提交时即时显示保存中并防重复提交；服务端确认持久化后显示保存成功，才能清理本次输入；失败显示具体下一步、保留输入并允许重试。网络超时/结果未知不能直接报告保存失败且鼓励盲目重复新增，开发时需核对幂等/确认机制。手机保存成功代表云端确认，不等同所有电脑已同步。

## 验收草案

- 点击保存立即有处理中反馈，处理期间不会重复提交。
- 服务端确认成功后可见成功反馈；不能仅发送请求就宣称成功。
- 明确失败保留输入，提供重试或重新登录等实际动作。
- 网络超时或结果不确定准确反馈，避免重复任务。

## 边界

本次仅记录，未授权编码、依赖安装、部署或GUI控制。实际代码层为backend/account-mobile.js，经Worker部署生效；实现前核对线上已有反馈链路，区分状态未显示、提示位置/时机或网络响应问题，不先假定完全没有反馈实现。

## 2026-10-02 开发批准

用户明确批准两项已记录优化进入开发。沿用gpt-6-luna / max、单人串行，独立Issue及本地提交；先保存反馈，再移除旧页面入口。先核对线上实际行为并执行相关行为回归及项目检查；不调用GUI、不安装新依赖、不自动部署或push，发布前提供准确diff与验证证据。

旧页面兼容策略：移除管理员旧入口和连接页面，旧页面导航到当前根登录页，不转发旧连接参数或密钥；后台旧API与Telegram不变。


## 开发记录（2026-10-02）

- Target version: 3.17.0（`feat` 次版本升级；版本字段同步 package.json、package-lock.json 与 manifest.json）。
- 手机端提交现在使用账号隔离的 sessionStorage 保存任务快照和稳定请求 ID；15 秒无响应会停止等待，保留输入，并提供复用同一 ID 的安全重试。服务器只在成功响应确认任务 ID 后清空表单。
- Worker 对同 ID、同内容的重试返回既有任务，不增加记录或同步修订；内容冲突拒绝覆盖；若同一请求关联任务已被其他设备删除，明确提示“重新添加”而不复活墓碑。
- 回归覆盖处理中双击拦截、请求超时、刷新恢复与安全重试、重新登录后延续确认、明确拒绝后的可编辑重试，以及已删除任务的确认/显式重加。
- 定向手机保存状态/安全重试测试与 Google 账号同步回归通过，相关文件 ESLint、`npm run typecheck`、`npm run lint` 通过。
- 完整 `npm run check` 在 `tests/ui-layout.test.mjs:32` 的既有源码顺序静态断言失败；该断言检查的共享 UI 文件未在本次修改范围内。
- 本需求以独立 Conventional Commit 本地提交；按批准范围不部署、不 push、不运行 GUI，因此线上用户尚未看到本次改动。

## 并发幂等补强（2026-10-02）

- 补充审查发现同时到达的同 UUID 重试可能都通过外部预读；即使任务主键不会重复，旧写入路径仍可能增加第二次同步修订。
- 手机带 `clientTaskId` 的创建现在在 D1 原子 batch 中使用“仅记录不存在时才提交”条件；同一 batch 包含 revision、change 和 record 三项写入，丢失竞争的一方读取规范记录并返回幂等结果，不更新时间戳、不增加 revision。没有新增迁移。
- 新并发回归用同 UUID/同内容/不同服务端时间同时创建，验证仅一条任务、一条同步变更、一个 revision，另一个请求得到 `alreadyProcessed`。
- 此并发补强以独立 `fix` 提交纳入 3.17.2；相关账号同步回归和 ESLint 通过。未部署或写生产 D1。
